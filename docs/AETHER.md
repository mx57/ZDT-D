# Исследование возможности интеграции движка Aether в ZDT-D и его эффективности для обхода ТСПУ/DPI в РФ

---

## 1. Введение и обзор Aether

**Aether** (разработчик CluvexStudio, [https://github.com/CluvexStudio/Aether](https://github.com/CluvexStudio/Aether)) — это клиент и ядро обхода цензуры на базе Rust, разработанное специально для использования в жестко ограниченных сетях.

В отличие от стандартных клиентов VPN/Proxy, Aether ориентирован на преодоление упреждающих блокировок:
- **MASQUE (HTTP/3 over QUIC и HTTP/2 over TLS)**: маскировка туннелируемого трафика под обычный HTTPS/QUIC.
- **TLS ClientHello Fragmentation (`--noize`)**: разбиение записей TLS ClientHello на этапе установки соединения HTTP/2 для преодоления SNI-фильтрации на DPI/ТСПУ.
- **Поддержка WireGuard и вложенных туннелей**:
  - `gool`: WireGuard-в-WireGuard (вложенный туннель);
  - `--mim`: MASQUE-в-MASQUE (HTTP/3 в HTTP/3 или HTTP/2 в HTTP/2) с получением отличного от исходного внешнего IP (Exit IP);
- **Автоматическое сканирование и валидация датаплейна (Data-plane validation)**: сканирование эндпоинтов Cloudflare WARP с проверкой фактического прохождения данных через туннель, а не только handshake.
- **Маркировка сокетов (`--mark`)**: возможность присваивать файрвольный марк открываемым сокетам для предотвращения зацикливания маршрутизации при работе через TUN.
- **Встроенная поддержка Tor (Arti) и Pluggable Transports**: возможность пропускать трафик через сеть Tor внутри MASQUE-туннеля или наоборот (`--tor`, `--tor-reverse`, `--tor-only`).
- **Локальный SOCKS5-прокси**: по умолчанию поднимает SOCKS5-сервер на `127.0.0.1:1819` (и опционально Tor SOCKS5 на `127.0.0.1:1820`).

## 2. Анализ архитектуры ZDT-D и моделей интеграции

### 2.1. Как работает ZDT-D
**ZDT-D** (Zero DPI Tunnel - Daemon) представляет собой систему маршрутизации трафика на Android с root-правами. В отличие от стандартных Android VPN-приложений, работающих через `VpnService`:
1. ZDT-D управляет трафиком на уровне ятра Linux, `iptables`/`ip6tables`, NFQUEUE, Android `netd` и разделения по UID (Linux User ID) приложений.
2. Рутовый демон `zdtd` выполняет резолвинг Android-пакетов в UID, управляет процессами движков и применяет правила файрвола/сетевых пространств.
3. Движки проксирования (например, `sing-box`, `mihomo`, `mieru`, `wireproxy`) запускаются локально и поддерживают две основные схемы маршрутизации.

### 2.2. Схемы интеграции Aether в ZDT-D

```
                                +-----------------------------------+
                                |     ZDT-D Daemon (zdtd root)     |
                                +-----------------+-----------------+
                                                  |
                         +------------------------+------------------------+
                         |                                                 |
            Схема 1: SOCKS5 + tun2socks + netd                Схема 2: Transparent Redirect (t2s)
                         |                                                 |
        +----------------v----------------+               +----------------v----------------+
        | Target Apps UIDs (Android netd) |               |  Target Apps UIDs (iptables)    |
        +----------------+----------------+               +----------------+----------------+
                         |                                                 |
        +----------------v----------------+               +----------------v----------------+
        |    TUN Interface (e.g. aetun0)  |               | iptables REDIRECT / TPROXY      |
        +----------------+----------------+               +----------------+----------------+
                         |                                                 |
        +----------------v----------------+               +----------------v----------------+
        |   tun2socks (TUN -> SOCKS5)     |               |   t2s (Transparent TCP -> SOCKS5)|
        +----------------+----------------+               +----------------+----------------+
                         |                                                 |
                         +------------------------+------------------------+
                                                  |
                                                  v
                               +------------------+------------------+
                               |    Aether (SOCKS5 127.0.0.1:1819)   |
                               +------------------+------------------+
                                                  |
                                                  v
                                      [ Internet / WARP / MASQUE ]
```

#### Схема 1: SOCKS5 + `tun2socks` + Android `netd` (Рекомендуемая для VPN-режима)
1. `zdtd` запускает бинарный файл `aether` с выбранным профилем (конфигом/флагами). Aether поднимает локальный SOCKS5 на `127.0.0.1:1819`.
2. `zdtd` запускает `tun2socks`, создавая виртуальный TUN-интерфейс (например, `aetun0`) и направляя его TCP/UDP трафик на SOCKS5-прокси `127.0.0.1:1819`.
3. Модуль `vpn_netd_builder` в `zdtd` создает виртуальную сеть в Android `netd` и привязывает выбранные UID приложений к интерфейсу `aetun0`.
4. **Преимущество**: Полная поддержка как TCP, так и UDP (включая DNS, игровые протоколы, QUIC), корректная работа раздельного туннелирования (Split Tunneling) по списку приложений.

#### Схема 2: Прозрачный редирект (Transparent Redirect via `t2s` / `iptables`)
1. `zdtd` запускает `aether` (SOCKS5 на `127.0.0.1:1819`).
2. Трафик выбранных UID перехватывается с помощью `iptables -t nat -A OUTPUT -m owner --uid-owner ... -j REDIRECT --to-ports <t2s_port>`.
3. Внутренний компонент `t2s` перенаправляет прозрачный TCP-трафик на SOCKS5-порт Aether.
4. **Преимущество**: Легковесность, отсутствие задействования TUN-интерфейса.
5. **Ограничение**: Поддерживает только TCP. UDP-трафик требует дополнительной обработки или блокировки (`blockedquic`).

## 3. Анализ эффективности против ТСПУ / DPI в РФ и Обхода "Белых Списков"

### 3.1. Текущая ситуация с блокировками в РФ (ТСПУ)
ТСПУ (Технические средства противодействия угрозам) в РФ используют следующие методы цензуры:
1. **Сигнатурный и протокольный анализ**: Распознавание WireGuard, OpenVPN, ShadowSocks, TLS/SNI, QUIC handshake.
2. **Блокировка QUIC / UDP/443**: Массовая глушилка или дроп UDP-пакетов на порту 443 для предотвращения использования QUIC/HTTP3 и WireGuard.
3. **Блокировка по IP-адресам Cloudflare / WARP**: Периодический бан пулов IP-адресов эндпоинтов WARP (`162.159.192.0/24`, `188.114.96.0/24` и др.) и портов 2408, 500, 1701, 4500.
4. **Фильтрация SNI / ClientHello**: Анализ поля SNI в TLS ClientHello для блокировки запрещенных доменов и обрыва TCP-сессий (RST).
5. **«Белые списки» (Whitelist mode) / Региональные блокировки**: В периоды жестких ограничений провайдеры пропускают только трафик к разрешенным доменам/IP (RU-сегмент), блокируя все внешние IP-адреса и непротоколируемые соединения.

### 3.2. Возможности Aether для обхода ТСПУ и DPI

| Технология Aether | Механизм действия | Эффективность против ТСПУ |
|---|---|---|
| **MASQUE over HTTP/2 (`--h2`)** | Мультиплексирование трафика внутри стандарта HTTP/2 over TLS (TCP/443) | **ВЫСОКАЯ**. В условиях глушения QUIC/UDP обходит блокировку UDP/443, так как работает поверх чистого TCP TLS. |
| **TLS ClientHello Fragmentation (`--noize firewall`)** | Разбиение первого пакета TLS ClientHello на фрагменты на уровне записей | **ВЫСОКАЯ**. DPI/ТСПУ не могут собрать SNI из первого TCP-сегмента без сигнатурного реассемблинга, что позволяет обходить SNI-блокировки. |
| **MASQUE over HTTP/3 (`--masque`)** | Передача данных по QUIC | **СРЕДНЯЯ / НИЗКАЯ в РФ**. Подвержен блокировке UDP/443 со стороны ТСПУ. Требуется переключение на `--h2`. |
| **Сканирование эндпоинтов (`--scan turbo/balanced`)** | Динамический поиск рабочих IP и портов Cloudflare с валидацией датаплейна | **ВЫСОКАЯ**. Автоматически находит «живые» эндпоинты Cloudflare, которые не попали в текущий бан-лист ТСПУ. |
| **Вложенный MASQUE (`--mim`)** | MASQUE inside MASQUE | **ВЫСОКАЯ**. Позволяет скрыть исходный адрес обращения и сменить Exit IP. |
| **Fwmark (`--mark 0xff`)** | Пометка сокетов Aether для правил `ip rule` | **КРИТИЧНА**. Позволяет открываемым Aether сокетам выходить напрямую через физический интерфейс, обходя TUN-маршрутизацию. |
| **Интеграция Tor (`--tor`)** | Проброс Tor внутри MASQUE-туннеля | **ОЧЕНЬ ВЫСОКАЯ**. Позволяет получить Tor Exit IP даже при блокировке Tor провайдером, так как сам Tor спрятан внутри зашифрованного MASQUE. |

### 3.3. Обход "Белых Списков" (Whitelist Mode) и доменная маршрутизация

Когда провайдер переходит в режим «белых списков» (пропускаются только соединения к разрешенным ресурсам, например, порталу Госуслуг, Яндекс, VK и т.д.):

1. **Доменная маршрутизация в Aether**:
   Aether поддерживает сопоставление правил маршрутизации по домену, IP и порту на основе SNI TLS. Это позволяет направлять трафик к "белым" ресурсам напрямую, а заблокированный трафик — через туннель.
2. **Upstream Proxy (`--upstream-proxy`)**:
   Aether может подключаться через уже существующий локальный прокси или VPN на устройстве. Если на устройстве есть доступ к прокси из белого списка, Aether может туннелировать свой трафик через него.
3. **Обход через фронтинг / разрешенные SNI (Domain Fronting)**:
   При использовании HTTP/2 MASQUE соединение устанавливается с IP-адресом CDN (например, Cloudflare), а поле SNI или заголовки HTTP/2 могут маскироваться под разрешенные ресурсы, проходящие через белые списки DPI.

## 4. Оценка технической совместимости Aether с Android и ZDT-D

### 4.1. Сборка и кросс-компиляция Aether под Android (ARM64 / x86_64)
Aether написан на Rust и использует биндинги C/C++ (библиотеку Cloudflare `quiche` и `CMake`).
- **Совместимость**: Aether успешно собирается под целевые триплеты Android:
  - `aarch64-linux-android` (основная архитектура Android)
  - `armv7-linux-androideabi`
  - `x86_64-linux-android`
- **Зависимости**: При статической сборке с `musl` (`aarch64-unknown-linux-musl`) или через Android NDK бинарный файл Aether представляет собой один автономный исполняемый файл размером ~8–12 МБ, не требующий внешних shared-библиотек (`.so`).
- **Разрешения**: На Android требуется доступ к `/dev/net/tun` (для TUN-режимов) или права root (для применения `--mark` и интеграции с `netd`), что полностью соответствует концепции ZDT-D.

### 4.2. Конфликтные ситуации и решение в ZDT-D

1. **Конфликт по портам**:
   По умолчанию Aether занимает SOCKS5 порт `1819` и RPC/Control порт `1820`.
   - *Решение*: В ZDT-D необходимо реализовать автоматический подбор свободных портов (`suggest_free_socks5_port`, `suggest_free_rpc_port`) и динамическую генерацию конфигурации для каждого профиля Aether.
2. **Блокировка QUIC приложениями (`blockedquic`)**:
   Поскольку ТСПУ часто глушит QUIC (UDP/443), рекомендуется использовать модуль ZDT-D `blockedquic` совместно с Aether в режиме `--h2` (HTTP/2), что принудительно переводит браузеры и приложения с QUIC на TCP/TLS HTTP/2.
3. **Зацикливание трафика (Routing Loop)**:
   При использовании Aether с `tun2socks` и Android `netd`, сокеты самого Aether должны быть исключены из туннеля.
   - *Решение*: Использование флага Aether `--mark 0xff` в сочетании с правилами `ip rule add fwmark 0xff lookup main priority 100`, либо исключение UID пользователя/процесса Aether из привязки `netd`.

## 5. Рекомендуемые конфигурации Aether для условий РФ

Для обеспечения максимальной доступности в РФ при интеграции Aether в ZDT-D рекомендуются следующие предустановленные профили:

### Профиль 1: "РФ ТСПУ Bypass (HTTP/2 + TLS Noise)" — *Основной рекомендуемый*
```bash
aether --h2 --scan balanced --noize firewall --bind 127.0.0.1:2090 --mark 0xff
```
* **Почему работает**: Использование HTTP/2 избегает блокировок UDP/443. Параметр `--noize firewall` фрагментирует TLS ClientHello, не позволяя ТСПУ определить SNI и заблокировать установку соединения.

### Профиль 2: "Deep Censorship / TOR Escape"
```bash
aether --h2 --noize firewall --tor --bind 127.0.0.1:2090 --mark 0xff
```
* **Почему работает**: Весь трафик передается внутри зашифрованного HTTP/2 туннеля до WARP, а выход в интернет осуществляется через Tor. Обеспечивает обход блокировок IP-адресов назначения и максимальную анонимность.

### Профиль 3: "Double MASQUE (--mim)"
```bash
aether --h2 --mim --noize firewall --bind 127.0.0.1:2090 --mark 0xff
```
* **Почему работает**: Двойной каскадный туннель с разными Exit IP, защищенный фрагментацией TLS.

## 6. Пошаговый план потенциальной реализации интеграции Aether в ZDT-D

Если в будущем будет принято решение о внедрении движка Aether в код ZDT-D, интеграция будет включать следующие этапы:

### Этап 1: Добавление бинарных файлов и скриптов сборки
1. Настройка кросс-компиляции Aether в NDK/Rust тулчейне для `aarch64-linux-android`.
2. Размещение бинарника `aether` в дистрибутиве модуля `/data/adb/modules/ZDT-D/bin/aether`.

### Этап 2: Создание Rust-модуля управления движком в `zdtd`
1. Создание файла `rust/zdtd/src/programs/aether.rs` по аналогии с `mieru.rs` и `singbox.rs`.
2. Реализация структур настроек (`ProfileSetting`):
   - `socks5_port`: u16 (по умолчанию 2090)
   - `protocol`: Enum (`H2`, `H3`, `WireGuard`, `Mim`, `Gool`)
   - `enable_noize`: bool (флаг `--noize firewall`)
   - `scan_mode`: Enum (`Turbo`, `Balanced`, `Off`)
   - `enable_tor`: bool (флаг `--tor`)
   - `tun`: String (имя интерфейса, например `aetun0`)
3. Реализация функций генерации профилей, управления процессами, проверки портов и создания объектов `VpnNetdProfile` для передачи в `vpn_netd_builder`.

### Этап 3: Регистрация Aether в ядре `zdtd`
1. Регистрация `aether` в `rust/zdtd/src/programs/mod.rs` и `settings.rs`.
2. Добавление вызова `aether::start_profiles_for_netd()` в общий цикл запуска VPN-профилей.
3. Добавление контроля конфликтов портов и TUN-интерфейсов.

### Этап 4: Поддержка в Android API и Compose UI
1. Создание DTO и API методов в Kotlin-приложении (`application/app/src/main/java/.../data/model/AetherProfile.kt`).
2. Добавление экрана настройки профилей Aether в UI (Jetpack Compose).
3. Добавление локализации на русском и английском языках (`strings.xml`).

## 7. Заключение

1. **Возможность интеграции**: **ДА, интеграция полностью возможна и архитектурно совместима.** Aether идеально вписывается в существующую модель ZDT-D (SOCKS5 + `tun2socks` + Android `netd`).
2. **Работоспособность на Android**: Aether нативно компилируется под ARM64 Android, не требует тяжелых зависимостей и эффективно работает с root-привилегиями ZDT-D.
3. **Эффективность против ТСПУ/DPI в РФ**: Aether является **одним из самых эффективных современных решений** благодаря сочетанию HTTP/2 MASQUE, фрагментации TLS ClientHello (`--noize`), сканирования эндпоинтов WARP и каскадных туннелей. В условиях жестких блокировок в РФ данная связка превосходит стандартные WireGuard и Unencrypted SOCKS/Shadowsocks решения.
